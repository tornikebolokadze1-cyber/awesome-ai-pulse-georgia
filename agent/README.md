# კოლექციის კურატორი აგენტი

ეს საქაღალდე Awesome AI Pulse Georgia-ს „კურატორს" შეიცავს — პროგრამას, რომელიც ყოველ დილით თავად ათვალიერებს სიას და GitHub-ს, ეძებს, რა შეიცვალა და რა გამოვიდა ახალი, და ცვლილებებს გთავაზობს. თვითონ არაფერს ცვლის: სია მხოლოდ შენი თანხმობის შემდეგ იცვლება. მასთან საუბარი Grok Bot-იდანაც შეიძლება.

წარმოიდგინე ბიბლიოთეკარის თანაშემწე. ყოველ დილით თაროებს ჩამოუვლის (სიაში არსებულ რეპოებს), გაზეთს გადაათვალიერებს (GitHub-ის ძიებას და Trending-ს), ყოველ მიგნებაზე ბარათს დაწერს და მაგიდაზე დაგიდებს. შენ ხელს აწერ ან უარს ეუბნები. ხელმოწერილ ბარათებს ის თავად ასრულებს, მაგრამ ჯერ კატალოგს ამოწმებს, რომ ყველაფერი ერთმანეთს ემთხვეოდეს.

## როგორ მუშაობს

**1. სკანი** — `.github/workflows/agent-scan.yml`, ყოველდღე 08:17-ზე თბილისის დროით. აგენტი სიაში არსებულ ყველა რეპოს ამოწმებს: ხომ არ წაიშალა, ხომ არ დაარქივდა, ხომ არ გადავიდა ახალ მისამართზე, ხომ არ ჩავიდა ~3,000 ვარსკვლავს ქვემოთ, ან წელზე მეტია ხომ არ განახლებულა. შემდეგ ახალ რეპოებს ეძებს. ყოველ მიგნებაზე იქმნება GitHub Issue (ჩანაწერი პროექტის „საკითხების" სიაში) ლეიბლით `agent:proposal`. ახალი რეპოს ქართულ აღწერას Claude წერს, მერე იმავე რეპოს README-სთან ადარებს და ფაქტებს ამოწმებს.

**2. დამტკიცება** — შენ. Grok Bot-ში ეუბნები „დაამტკიცე #12", ან GitHub-ზე Issue-ს ამატებ ლეიბლს `agent:approved`. უარისთვის — `agent:rejected`.

**3. შესრულება** — `.github/workflows/agent-apply.yml`. დამტკიცება ამ workflow-ს (ავტომატურ სამუშაო პროცესს GitHub-ზე) რთავს. სამუშაო სამ ცალკე ნაწილად (job-ად) არის გაყოფილი, ერთი წესით: ვინც სხვების დაწერილ კოდს უშვებს, რეპოში ჩაწერის გასაღები არ აქვს, და ვისაც ეს გასაღები აქვს, სხვების კოდს არ უშვებს. პირველი ნაწილი (`prepare`) README-ს ცვლის, ყველა ციფრს ასწორებს (ბეჯები, ბანერი, საიტი, MCP-ის აღწერები), MCP-ის და საიტის მონაცემებს თავიდან აწყობს და ყველა შემოწმებას უშვებს — npm პაკეტების (სხვების დაწერილი კოდის) დახმარებით, მაგრამ რეპოში ჩაწერის უფლების გარეშე. მეორე ნაწილს (`push`) ჩაწერის უფლება აქვს, მაგრამ npm-ის არც ერთ პაკეტს არ უშვებს: მზა ცვლილებას მონაცემად ამოწმებს (მხოლოდ ნებადართული ფაილები; ციფრების ფაილებში მხოლოდ ციფრები; README-ში მხოლოდ ცხრილის რიგები და ციფრები; მონაცემების ფაილებში მხოლოდ JSON), ინახავს main-ზე ერთ commit-ად (შენახვის წერტილად) და MCP სერვერის npm-ზე გამოქვეყნებას რთავს. მესამე ნაწილი (`tell`) Issue-ს ხურავს ამ commit-ის ბმულით. თუ commit-მდე რამე ვერ გაიარა, არაფერი ინახება და Issue-ზე წერია, რატომ. npm-ზე გამოქვეყნება კი commit-ის შემდეგ იწყება, ამიტომ მისი ჩავარდნა სიას აღარ აბრუნებს (იხ. „როცა რამე არ მუშაობს").

**4. Grok-ის კარიბჭე** — `src/gateway.ts`. პატარა სერვერი Deploy ON-ზე, რომელსაც Grok MCP-ით (Model Context Protocol — სტანდარტი, რომლითაც AI ასისტენტები გარე ხელსაწყოებს იძახებენ) ესაუბრება. ის კოლექციას კითხულობს, შეთავაზებებს გაჩვენებს და დამტკიცებისას მხოლოდ ლეიბლს ამატებს. ფაილების შეცვლა არ შეუძლია. grok.com Header-ს ვერ აგზავნის, ამიტომ კარიბჭე მას OAuth-ით, საკუთარი შესვლის გვერდით უშვებს (`src/oauth.ts`).

**5. შენი შეთავაზებები** — `.github/workflows/agent-suggest.yml`. როცა შენ ქმნი Issue-ს ლეიბლით `agent:suggestion` (ან Grok-ს სთხოვ, `suggest_repo`), აგენტი რეპოს წესებით აფასებს და პასუხს იქვე წერს: ან დამატების შეთავაზებას ქმნის, ან გეუბნება, რატომ არა. ასეთ დამატებას მხოლოდ GitHub-ზე ამტკიცებ, ლეიბლით: შეთავაზება შეიძლება თვითონ Grok-იდან მოვიდა, ამიტომ მისი დამტკიცებაც Grok-ს არ შეუძლია.

## რა არის დაცული

სიაში არაფერი იცვლება შენი დამტკიცების გარეშე. სრულდება მხოლოდ ის Issue, რომელიც აგენტმა (`github-actions[bot]`) ან შენ შექმენი — სხვისი ჩანაწერი, თუნდაც `agent:approved` ლეიბლით, უარყოფილია. დამტკიცებად კი ითვლება მხოლოდ ის ლეიბლი, რომელიც შენმა ანგარიშმა დაამატა: სხვა ვინმემ რომც დაამატოს, შესრულებისას უარყოფილი იქნება. Grok შენი ტოკენით მუშაობს, ამიტომ მისი დამტკიცება შენად ითვლება. აკრძალული სია (`config/rules.json` → `exclude`: sub2api, heretic, DSH-ის ეკოსისტემა, watermark-ის წამშლელები და სხვ.) არასოდეს შემოდის, არც შენი შეთავაზებით. დამატებამდე აგენტი იმ დღის ციფრებით კიდევ ერთხელ ამოწმებს, რომ რეპო არ დაარქივებულა, fork (სხვისი რეპოს ასლი) არ არის, ნაყიდი ვარსკვლავების ნიშნები არ აქვს და ზღვარს ზემოთაა. ამოღება, შენიშვნა და ინგლისური აღწერა იგივენაირად მოწმდება: რეპო, რომელიც მას შემდეგ დაბრუნდა, სიაში რჩება; შენიშვნის ტექსტი GitHub-ის ბოლო ცვლილების თარიღიდან იწერება და არა Issue-დან; ინგლისური აღწერა კი მხოლოდ მაშინ იწერება, თუ GitHub-ზე ზუსტად ეს ტექსტი წერია. სრულდება ზუსტად ის, რაც Issue-ში წაიკითხე: თუ Issue-ს ტექსტი აგენტის დაწერილს არ ემთხვევა, ან ვინმემ ის შემდეგ შეცვალა (edit), შესრულებაზე უარს ამბობს — ასეთი Issue დახურე, და სკანი (ან შენი ახალი შეთავაზება) მას თავიდან შექმნის. ყოველი შესრულება ერთი commit-ია, ამიტომ ერთი ბრძანებით ბრუნდება.

ერთი რამ პირდაპირ უნდა გითხრა: Grok-ს სერვერი ეუბნება, რომ დაამტკიცოს მხოლოდ შენი პირდაპირი „კი"-ს შემდეგ, მაგრამ ეს მოდელისთვის მიცემული მითითებაა და არა საკეტი. თუ Grok-ს ოდესმე რომელიმე ვებგვერდი ან შეთავაზების ტექსტი შეაცდენს, მას ერთდროულად რამდენიმე ღია შეთავაზების დამტკიცება შეუძლია (გარდა შენი შეთავაზებებიდან მოსული დამატებებისა — მათ კარიბჭე Grok-ს არ ამტკიცებინებს). თითოეული მაინც ყველა შემოწმებას გადის და ერთი commit-ით ბრუნდება, მაგრამ სიაში მოხვდება, სანამ არ შეამჩნევ. უფრო სერიოზული შემთხვევაა, თუ კარიბჭის GitHub-ის ტოკენი (PAT) გაჟონავს: მისით სხვას შეუძლია შენი სახელით შეთავაზება შექმნას და თვითონვე დაამტკიცოს. ამიტომ ტოკენი მხოლოდ ამ ერთ რეპოზე მუშაობს, მხოლოდ ქვემოთ ჩამოთვლილი უფლებები აქვს და 90 დღეში იწურება. თუ Issues-ში ან commit-ებში უცნობ რამეს დაინახავ, ტოკენი GitHub-ზე მაშინვე გააუქმე. Grok-ის დროებითი გასაღებებიც გასაღებებია: თუ ისინი Grok-ის მხრიდან გაჟონავს, მათით კარიბჭის ყველა ხელსაწყოს გამოყენება შეიძლება, სანამ შენი შესვლიდან 90 დღე არ გავა ან `MCP_TOKEN`-ს არ შეცვლი.

კიდევ ერთი საზღვარი: შესრულების პირველი ნაწილი npm პაკეტებს უშვებს. თუ რომელიმე მათგანი ოდესმე მავნე ვერსიით შეიცვლება, მას რეპოში ჩაწერის უფლება მაინც არ ექნება, მეორე ნაწილი კი მისგან მხოლოდ ნებადართულ ფაილებს მიიღებს, და მათშიც ციფრების ფაილებში მხოლოდ ციფრებს, README-ში მხოლოდ ცხრილის რიგებსა და ციფრებს, ხოლო მონაცემებში მხოლოდ JSON-ს. რას წერს თვითონ რიგი, ამას ეს შემოწმება ვერ განსჯის, ამიტომ ყოველ შესრულების commit-ს თვალი მაინც გადაავლე. npm პაკეტები სხვა სამ ადგილასაც ეშვება: შესრულების მესამე ნაწილში, დღიურ სკანში და შენს შეთავაზებებზე პასუხისას. იქ მავნე ვერსია რეპოში ვერაფერს ჩაწერს, მაგრამ Issues-ში კომენტარის დაწერას, ლეიბლის დამატებას და Issue-ს დახურვას შეძლებს, სკანსა და შეთავაზებებზე პასუხში კი — Claude-ის გასაღების წაკითხვასაც. სწორედ ამიტომ გჭირდება ხარჯის ლიმიტი Anthropic Console-ში.

## ერთჯერადი გამართვა

### 1. Claude-ის გასაღები (აღწერების დასაწერად)

1. გახსენი console.anthropic.com → API Keys → Create Key და დააკოპირე გასაღები.
2. იქვე, Billing-ში, დააწესე თვიური ხარჯის ლიმიტი — ასე ხარჯი შენს კონტროლშია.
3. GitHub-ზე: რეპო → Settings → Secrets and variables → Actions → New repository secret. სახელი: `ANTHROPIC_API_KEY`, მნიშვნელობა: გასაღები.
4. სურვილისამებრ, იმავე გვერდის Variables ჩანართში შეგიძლია დაამატო `AGENT_MODEL`, თუ სხვა მოდელი გინდა. ნაგულისხმევია `claude-sonnet-5-5`.

გასაღების გარეშეც მუშაობს: ჯანმრთელობის შემოწმება და ინგლისური აღწერების განახლება ხდება, მხოლოდ ახალი რეპოები და აღწერების გადახედვა ელოდება გასაღებს.

### 2. პირველი სკანი

GitHub → Actions → Agent scan → Run workflow. 10–20 წუთში Issues-ში შეთავაზებები გამოჩნდება.

### 3. კარიბჭე Deploy ON-ზე

**ა) GitHub-ის ტოკენი** — fine-grained PAT (პირადი წვდომის გასაღები, რომელიც მხოლოდ ამ ერთ რეპოზე მუშაობს). github.com → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token:

- Repository access: Only select repositories → `awesome-ai-pulse-georgia`
- Permissions: Actions — Read and write (სკანის გასაშვებად); Issues — Read and write (შეთავაზებებისთვის); Contents — Read-only (ფაილების წასაკითხად). Metadata ავტომატურად ემატება. სხვა არაფერი მისცე.
- Expiration: 90 დღე. ვადის გასვლისას ახალს შექმნი და Deploy ON-ში შეცვლი.

**გ) სერვისი Deploy ON-ზე** — ახალი სერვისი ამ GitHub რეპოდან:

შემოწმება: ბრაუზერში გახსენი `https://<სერვისის-მისამართი>/healthz` — უნდა ჩანდეს `{"ok":true,"service":"aipulse-georgia-agent"}`.

### 4. Grok-ის დაკავშირება

grok.com-ის Custom Connector-ს Header-ის ველი არ აქვს: სერვერს OAuth-ით, ანუ ბრაუზერში ერთჯერადი შესვლით უკავშირდება. ამისთვის კარიბჭეს საკუთარი შესვლის გვერდი აქვს, სადაც `MCP_TOKEN`-ს ერთხელ ჩასვამ. თვითონ ამ გასაღებს Grok ვერ ხედავს: ის საათიან დროებით გასაღებს იღებს, რომელიც სტანდარტული კლიენტი თავად აახლებს. თავიდან დაკავშირება დაგჭირდება, თუ connector-ს 30 დღე არ გამოიყენებ, და ყოველ შემთხვევაში შესვლიდან 90 დღის შემდეგ: ასე გაჟონილი დროებითი გასაღებიც სამუდამოდ ვერ იმუშავებს.

1. grok.com → Connectors → New Connector → Custom. URL: `https://<სერვისის-მისამართი>/mcp`
2. „OAuth Credentials Required" ფორმაში:
   - Client ID: `aipulse-grok` (კარიბჭე ნებისმიერ სახელს იღებს, ეს უბრალოდ წარწერაა)
   - Client Secret: ცარიელი
   - Authorization Endpoint: `https://<სერვისის-მისამართი>/oauth/authorize`
   - Token Endpoint: `https://<სერვისის-მისამართი>/oauth/token`
   - Scopes: `mcp`
   - Token Auth Method: `none (PKCE only, recommended)`

   Endpoint-ები შეიძლება თავისით შეივსოს. მაშინ მხოლოდ შეამოწმე, რომ ზემოთ მოცემულს ემთხვევა.
3. Connect-ზე გაიხსნება კარიბჭის გვერდი „Grok-ის დაკავშირება აგენტთან". ჩასვი `MCP_TOKEN`, დააჭირე „დაკავშირება" და Grok-ში დაბრუნდები. `MCP_TOKEN` ამ გვერდზე მხოლოდ მაშინ ჩაწერე, როცა Connect-ს წამის წინ თავად დააჭირე — არასოდეს ვინმეს გამოგზავნილი ბმულით.
4. შემოწმება: ჰკითხე Grok-ს „რამდენი რეპოა კოლექციაში?", მერე „რა შეთავაზებები გვაქვს?". მეორე პასუხი GitHub-ის ტოკენსაც ამოწმებს.

Grok-ის გასათიშად connector-ი Grok-შივე წაშალე. ეს უკვე გაცემულ დროებით გასაღებებს არ აუქმებს: კარიბჭე მათ არსად ინახავს, ამიტომ თითოს ცალკე ვერ „გააუქმებს". თუ ფიქრობ, რომ რომელიმე გასაღები სხვის ხელშია, Deploy ON-ში `MCP_TOKEN` შეცვალე და სერვისი გადატვირთე: მანამდე გაცემული ყველა დროებითი გასაღები მაშინვე აღარ იმუშავებს, Grok-ს კი ახალი გასაღებით თავიდან დაუკავშირებ.

კლიენტს, რომელსაც Header-ის გაგზავნა შეუძლია (Grok CLI, xAI API), შესვლა არ სჭირდება: ის `Authorization: Bearer <MCP_TOKEN>`-ს აგზავნის.

## წესები ერთ ფაილში

`config/rules.json` — აგენტი მას ყოველ გაშვებაზე კითხულობს, ამიტომ რიცხვის შესაცვლელად კოდის შეხება არ გჭირდება. ზუსტი მნიშვნელობები მხოლოდ იქ წერია, რომ ორ ადგილას ორი სხვადასხვა რიცხვი არ დაგვრჩეს; აქ მხოლოდ ის არის, რას ნიშნავს თითოეული:

| პარამეტრი | რას ნიშნავს |
|---|---|
| `minStarsNew`, `discoverWindowDays` | ამდენ დღეზე ახალ რეპოს ამდენი ვარსკვლავი სჭირდება |
| `minStarsOld` | უფრო ძველ, ჯერ არშეტანილ რეპოს — ამდენი |
| `floorIndependent` × `floorSlack` | დამოუკიდებელი პროექტის ზღვარი და რამდენად ქვემოთ ჩასვლისას ამოიღება (ოფიციალურ ვენდორებს არ ეხება) |
| `minForkRatio`, `minCommits` | ნაყიდი ვარსკვლავების ნიშნები |
| `staleMonths` | ამდენი თვე განახლების გარეშე — თარიღიანი შენიშვნა |
| `maxNewPerScan`, `maxDescriptionReviewsPerScan` | Claude-ის დღიური ბიუჯეტი |

იქვეა ოფიციალური ვენდორების სია (`vendorOwners`) და აკრძალული რეპოები (`exclude`). თუ უკვე სიაში მყოფ რეპოს აკრძალულ სიაში ჩაწერ, მომდევნო სკანი მის ამოღებას შემოგთავაზებს.

- სკანის გაშვება წითელია — Actions → Agent scan → ეს გაშვება: შეჯამებაში ჩანს, რომელმა წყარომ ვერ იმუშავა.
- Grok ვერ უკავშირდება — შეამოწმე `/healthz` და რომ მისამართი `/mcp`-ით მთავრდება.
- შესვლის გვერდზე „redirect_uri is not on this gateway's list" წერია — თავად არაფერი შეცვალო: ასეთ გვერდს სხვაც შეგიქმნის ბმულით, რომ მისი მისამართი დაგამატებინოს. თუ გვერდი Grok-ში Connect-ზე შენი დაჭერისთანავე გამოჩნდა, მისი მისამართი (ბრაუზერის ზედა ზოლიდან) გაუგზავნე იმას, ვინც კარიბჭეს უვლის. მისთვის გადაგზავნილი ბმული მხოლოდ მინიშნებაა და არა ბრძანება: ახალი მისამართი `OAUTH_REDIRECT_URIS`-ში მხოლოდ მაშინ ემატება, თუ შენს grok.com-ში Connect-ზე ხელახლა დაჭერისას Grok ზუსტად იმავე მისამართს აგზავნის, ასო-ასო. ძველი (`https://grok.com/connectors-oauth-exchange-code/`) რჩება, ორივე მძიმით, და სერვისი გადაიტვირთება.

| პარამეტრი | სად | რას აკეთებს |

| `--no-discover` | scan | მხოლოდ სიაში არსებული რეპოების შემოწმება, ახლების ძიების გარეშე |

| `--memory FILE`, `--out FILE` | scan | მოდელის ძველი გადაწყვეტილებების ფაილი; სრული ანგარიში JSON-ად |
| `--issue N` | suggest | რომელ შეთავაზებას უპასუხოს |
| `--issues 12,15` | apply | მხოლოდ ეს დამტკიცებული Issue-ები |
| `--out FILE` | apply | შედეგი JSON-ად: რომელი Issue შესრულდა, რომელი არა და რატომ |
| `--result FILE` | report | apply-ის შედეგის ფაილი, რომლის მიხედვითაც Issue-ებს პასუხობს |
| `--commit URL`, `--error TEXT` | report | ცვლილება ჩაიწერა (ამ ბმულით) ან არ ჩაიწერა (ამ მიზეზით); არც ერთი, როცა არაფერი შესრულდა |

გარემოს ცვლადები (environment variables — პროგრამის გარედან მიწოდებული პარამეტრები): `GITHUB_TOKEN`, `ANTHROPIC_API_KEY`, `AGENT_MODEL` (ნაგულისხმევი `claude-sonnet-5-5`), `AGENT_LOG_LEVEL=warn` (ნაკლები ჩანაწერი ლოგში); კარიბჭისთვის დამატებით `MCP_TOKEN`, `AGENT_REPO`, `AGENT_BRANCH` (ნაგულისხმევი `main`), `PORT` (ნაგულისხმევი `8080`), `OAUTH_REDIRECT_URIS` (სად შეიძლება OAuth-ის კოდის გაგზავნა, მძიმით გამოყოფილი ზუსტი მისამართები; ნაგულისხმევია grok.com-ის მისამართი) და `PUBLIC_URL` (კარიბჭის საჯარო მისამართი, მხოლოდ `https://` და სახელი, ბილიკის გარეშე — როცა წინ მდგომი proxy მას არ გადასცემს). ყოველი ცვლადი მხოლოდ ჩართვისას იკითხება, ამიტომ მისი შეცვლის შემდეგ სერვისი გადატვირთე.
